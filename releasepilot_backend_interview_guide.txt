1. BACKEND PROJECT OVERVIEW
==================================================

What ReleasePilot Does:
ReleasePilot is a multi-tenant Feature Flag and Progressive Rollout SaaS backend. It provides centralized feature flag lifecycle management, deterministic percentage-based progressive rollouts, attribute-based user targeting rules, evaluation result caching, mutation audit logging, and OpenAI-powered rollout insights.

What Problem It Solves:
It decouples software deployment from feature release. Engineering teams can push code to production behind feature flags and safely toggle features ON/OFF, run canary/A-B test rollouts to specific user subsets, or instantly kill malfunctioning code in real-time without redeploying applications or restarting servers.

Backend Responsibilities:
1. Multi-tenant Org & Project Isolation (JWT authenticated CRUD APIs for Orgs, Projects, Environments, Flags, Rules).
2. Ultra-low Latency Rule & Flag Evaluation Engine (< 5ms) for external applications via API Keys.
3. Deterministic Consistent Hashing (SHA-256) for percentage-based rollout bucketing.
4. Distributed Cache Management (Spring Cache abstraction over Redis).
5. Mutation Audit Trail Persistence & Async Evaluation Activity Logging.
6. External AI Integration for rollout risk assessment (OpenAI Chat Completions).

Tech Stack:
- Programming Language: Java 21
- Framework: Spring Boot 4.1.0
- Security: Spring Security 6.x (Stateless JWT + Custom API Key filter logic)
- Database: PostgreSQL 17 (relational persistence)
- ORM / Persistence: Spring Data JPA / Hibernate 6.x
- Database Migrations: Flyway (SQL migrations V1–V4)
- Cache: Redis 7 (Spring Data Redis with GenericJackson2JsonRedisSerializer)
- API Documentation: springdoc-openapi 3.1 (Swagger UI at /swagger-ui.html)
- Serialization: Jackson ObjectMapper
- Build Tool: Maven (Java 21 target)
- Containerization: Docker & Docker Compose (multi-stage Dockerfile)

Backend Architecture:
ReleasePilot strictly follows a layered REST Controller -> Service -> Repository -> Database architecture.

Where Features Fit:
- JWT: Evaluated in JwtAuthenticationFilter before hitting Controllers.
- Redis: Intercepts EvaluationService.evaluateFlag() using Spring CacheManager.
- Feature Flag Evaluation & Progressive Rollout: Executed in EvaluationService.performEvaluation() & HashUtils.getBucket().
- Flyway: Runs at Spring Boot startup before Hibernate initializes schema or processes queries.

3. CONTROLLER → SERVICE → REPOSITORY ARCHITECTURE
==================================================

Why ReleasePilot Separates Layers:
1. Controller Layer: Handles HTTP protocol concerns (request mapping, path variables, DTO validation, HTTP status code wrapping).
2. Service Layer: Contains core business logic, transaction boundaries (@Transactional), rule evaluation algorithms, caching, and cross-cutting audit invocation. Completely decoupled from HTTP request/response objects.
3. Repository Layer: Encapsulates database access queries using Spring Data JPA abstractions, decoupling domain logic from SQL persistence.

Complete Trace 1: SDK Flag Evaluation (POST /api/v1/eval/evaluate)

1. HTTP Request:
   Headers: X-API-Key: dev_key_123, Content-Type: application/json
   Body: {"flagKey": "new-checkout", "context": {"userId": "usr_99", "country": "US"}}

2. Controller:
   FILE: src/main/java/com/releasepilot/feature/EvaluationController.java
   CLASS: EvaluationController
   METHOD: evaluateFlag(@RequestHeader("X-API-Key") String apiKey, @Valid @RequestBody EvaluateRequest request)
   Action: Extracts header and body, calls evaluationService.evaluateFlag(apiKey, request).

3. Service:
   FILE: src/main/java/com/releasepilot/feature/EvaluationService.java
   CLASS: EvaluationService
   METHOD: evaluateFlag(String apiKey, EvaluateRequest request)
   Action:
   a. Fetches Environment by apiKey via environmentRepository.findByApiKey(apiKey).
   b. Fetches FeatureFlag by projectId and flagKey via featureFlagRepository.findByProjectIdAndKey(...).
   c. Generates cache key using SHA-256 digest ofTreeMap(context).
   d. Checks Redis via getCachedResult(cacheKey). If hit, returns immediately.
   e. If miss, calls performEvaluation(flag, environment, context).
   f. Writes evaluation log asynchronously to evaluationLogRepository.save(log).

4. Repository:
   FILE: src/main/java/com/releasepilot/project/EnvironmentRepository.java
   METHOD: findByApiKey(String apiKey)
   Query executed: SELECT * FROM environments WHERE api_key = ?

   FILE: src/main/java/com/releasepilot/feature/FeatureFlagRepository.java
   METHOD: findByProjectIdAndKey(UUID projectId, String key)
   Query executed: SELECT * FROM feature_flags WHERE project_id = ? AND key = ?

5. PostgreSQL: Executes queries over indexed columns (api_key, project_id, key).

6. Response: Returns HTTP 200 OK with ApiResponse<EvaluationResultDto>:
   {"success": true, "data": {"flagKey": "new-checkout", "value": true, "reason": "TARGET_MATCH", "environmentKey": "dev"}}

   - Creates audit_logs table.
   - Creates evaluation_logs table.

Flyway vs JPA Relationship:
Flyway owns DDL (table structures, constraints, indexes). Hibernate's ddl-auto is set to `validate`, verifying that JPA entity annotations match the Flyway database schema exactly.

6. JWT + SPRING SECURITY
==================================================

Authentication Architecture & Flow:

1. Registration (POST /api/v1/auth/register)
   FILE: src/main/java/com/releasepilot/auth/AuthService.java
   METHOD: register(RegisterRequest request)
   WHAT HAPPENS: Checks if user email exists. Encrypts password using BCryptPasswordEncoder. Saves User entity. Auto-provisions default Organization and starter Project with 'dev', 'staging', 'prod' Environments. Returns JWT token.

2. Login (POST /api/v1/auth/login)
   FILE: src/main/java/com/releasepilot/auth/AuthService.java
   METHOD: login(AuthRequest request)
   WHAT HAPPENS: Calls authenticationManager.authenticate(new UsernamePasswordAuthenticationToken(email, password)). If valid, invokes jwtTokenProvider.generateToken(authentication) and returns AuthResponse containing JWT string.

3. Password Hashing
   FILE: src/main/java/com/releasepilot/security/PasswordEncoderConfig.java
   BEAN: PasswordEncoder passwordEncoder() -> returns new BCryptPasswordEncoder().

4. User Lookup
   FILE: src/main/java/com/releasepilot/security/CustomUserDetailsService.java
   METHODS: loadUserByUsername(String email), loadUserById(UUID id)
   WHAT HAPPENS: Queries UserRepository and wraps returned User entity in UserPrincipal (implements Spring Security UserDetails).

5. JWT Creation & Claims
   FILE: src/main/java/com/releasepilot/security/JwtTokenProvider.java
   METHOD: generateTokenFromUserId(UUID userId, String email)
   WHAT HAPPENS:
   - Subject: userId.toString()
   - Claim "email": email
   - IssuedAt: current date
   - Expiration: current date + 86400000 ms (24 hours)
   - Signature: HMAC-SHA256 using key derived from jwt.secret property.

6. JWT Validation & Security Filter
   FILE: src/main/java/com/releasepilot/security/JwtAuthenticationFilter.java
   METHOD: doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain)
   WHAT HAPPENS:
   a. Extracts "Authorization: Bearer <token>" header via getJwtFromRequest().
   b. Calls tokenProvider.validateToken(jwt).
   c. Parses userId via tokenProvider.getUserIdFromJWT(jwt).
   d. Loads UserDetails via customUserDetailsService.loadUserById(userId).
   e. Instantiates UsernamePasswordAuthenticationToken and sets it in SecurityContextHolder.getContext().setAuthentication(...).

7. Protected vs Permitted Endpoints
   FILE: src/main/java/com/releasepilot/security/SecurityConfig.java
   METHOD: filterChain(HttpSecurity http)
   Permitted: /api/v1/auth/**, /api/v1/eval/**, /actuator/health, /swagger-ui/**.
   Protected: All other routes (/api/v1/projects/**, /api/v1/flags/**, etc.) require valid JWT Bearer header.

7. REDIS CACHING
==================================================

Actual Redis Implementation Analysis:

1. Configuration & Enablement:
   FILE: src/main/java/com/releasepilot/config/RedisCacheConfig.java
   CLASS: RedisCacheConfig
   - Annotated with @Configuration, @EnableCaching, and @ConditionalOnProperty(name = "releasepilot.cache.enabled", havingValue = "true").
   - If releasepilot.cache.enabled is false (default in application.yaml), RedisCacheConfig is NOT loaded into Spring context.

2. Cache Manager & Serializer:
   BEAN: RedisCacheManager cacheManager(RedisConnectionFactory connectionFactory, ReleasePilotProperties properties)
   - TTL: Configured dynamically via releasepilot.cache.ttl-seconds (default: 30 seconds).
   - Serializer: GenericJackson2JsonRedisSerializer (serializes DTO objects to JSON strings in Redis).

3. Data Cached:
   Cache Name: "evaluations"
   Cached Object: EvaluationResultDto (contains flagKey, value, reason, environmentKey).

4. Key Structure:
   FILE: src/main/java/com/releasepilot/feature/EvaluationService.java
   METHOD: buildCacheKey(UUID environmentId, String flagKey, Map<String, Object> context)
   Structure: SHA-256 Hex Digest of string: environmentId + ":" + flagKey + ":" + objectMapper.writeValueAsString(new TreeMap<>(context))
   Example Key: "a3f8b912c4..." (64-character SHA-256 hex string).

5. Read / Write / Fallback Logic:
   FILE: src/main/java/com/releasepilot/feature/EvaluationService.java
   METHODS: getCachedResult(cacheKey), putCachedResult(cacheKey, result)
   - Cache Manager Injection: @Autowired(required = false) private CacheManager cacheManager;
   - If Redis is disabled (cacheManager is null) or Redis is unreachable, getCachedResult returns null (Cache Miss fallback).
   - If enabled:
     Cache Hit: Returns cached EvaluationResultDto directly, bypassing database rules evaluation.
     Cache Miss: Performs DB rules evaluation, calls putCachedResult(cacheKey, result) to store entry in Redis with TTL.

Redis Invalidation:
NOT IMPLEMENTED
Note: Cache entries automatically expire via TTL (30s). Manual cache eviction on flag update (e.g. @CacheEvict) is NOT implemented.

8. FEATURE FLAGS (CORE BUSINESS LOGIC)
==================================================

Feature Flag Lifecycle & Evaluation Pipeline:

1. Creation
   FILE: src/main/java/com/releasepilot/feature/FeatureFlagService.java
   METHOD: createFlag(UUID projectId, CreateFeatureFlagRequest request)
   - Saves FeatureFlag entity in `feature_flags` table.
   - Automatically iterates over all Environments in the Project and creates a corresponding `FlagEnvironment` entity for each environment (defaulting enabled = true).

2. Evaluation Pipeline (Tracing evaluateFlag in EvaluationService.java)
   FILE: src/main/java/com/releasepilot/feature/EvaluationService.java
   METHOD: performEvaluation(FeatureFlag flag, Environment environment, Map<String, Object> context)

   Step 1: Global Flag Enabled Check
   If flag.getEnabled() is false -> returns defaultServeValue with reason FLAG_DISABLED.

   Step 2: Environment Flag Check
   Look up FlagEnvironment by (flagId, environmentId). If missing or flagEnv.getEnabled() is false -> returns defaultServeValue with reason ENVIRONMENT_DISABLED.

   Step 3: Targeting Rules Check
   Fetches targeting rules ordered by priority ASC: targetingRuleRepository.findByFlagEnvironmentIdOrderByPriorityAsc(flagEnv.getId()).
   Iterates through rules. Evaluates evaluateTargetingRule(rule, context).
   If matched -> returns rule.getServeValue() with reason TARGET_MATCH.

   Step 4: Percentage Rollout Check
   Fetches RolloutRule for flagEnv.
   If present -> calculates bucket integer via HashUtils.getBucket(flag.getKey() + ":" + attrValue).
   If bucket < rollout.getPercentage() -> returns serveValueA; else -> serveValueB with reason PERCENTAGE_ROLLOUT.

   Step 5: Default Fallback
   Returns flagEnv.getServeValue() (or flag.getDefaultServeValue()) with reason DEFAULT_VALUE.

9. PROGRESSIVE ROLLOUT (DETERMINISTIC CONSISTENT HASHING)
==================================================

Determining How Percentage Rollout Works:
ReleasePilot does NOT use random numbers, TreeMap, or database counter tables for percentage rollouts.
It uses Deterministic SHA-256 Hashing over user context attributes.

Tracing the Code:

FILE: src/main/java/com/releasepilot/feature/EvaluationService.java
METHOD: performEvaluation(...) [Lines 119-131]

```java
Optional<RolloutRule> rolloutOpt = rolloutRuleRepository.findByFlagEnvironmentId(flagEnv.getId());
if (rolloutOpt.isPresent()) {
    RolloutRule rollout = rolloutOpt.get();
    String attrKey = rollout.getAttribute() != null ? rollout.getAttribute() : "userId";
    String attrValue = context.containsKey(attrKey) ? String.valueOf(context.get(attrKey)) : UUID.randomUUID().toString();

    int bucket = HashUtils.getBucket(flag.getKey() + ":" + attrValue);
    if (bucket < rollout.getPercentage()) {
        return buildResult(flag, rollout.getServeValueA(), EvaluationReason.PERCENTAGE_ROLLOUT, environment.getKey());
    } else {
        return buildResult(flag, rollout.getServeValueB(), EvaluationReason.PERCENTAGE_ROLLOUT, environment.getKey());
    }
}
```

FILE: src/main/java/com/releasepilot/common/HashUtils.java
CLASS: HashUtils
METHOD: getBucket(String input)

```java
public static int getBucket(String input) {
    try {
        MessageDigest md = MessageDigest.getInstance("SHA-256");
        byte[] digest = md.digest(input.getBytes(StandardCharsets.UTF_8));
        
        // Take first 4 bytes to form a 32-bit integer via bitwise shifts
        int hash = ((digest[0] & 0xFF) << 24) |
                   ((digest[1] & 0xFF) << 16) |
                   ((digest[2] & 0xFF) << 8)  |
                   (digest[3] & 0xFF);

        return Math.abs(hash % 100);
    } catch (Exception e) {
        return Math.abs(input.hashCode() % 100);
    }
}
```

How it Works mathematically:
1. Input string: `"new-checkout:usr_9981"`
2. SHA-256 Digest: Produces 32 deterministic bytes.
3. Bitwise shifting converts 4 bytes to 32-bit integer: `((b0 & 0xFF) << 24) | ...`
4. Modulo 100: `Math.abs(hash % 100)` yields an integer in `[0, 99]`.
5. Evaluation: If percentage is 30% (i.e. bucket 0..29), users with bucket < 30 receive serveValueA.
6. Guaranteed Properties: Statistically uniform distribution across 100 buckets, 100% deterministic (same user always gets same result), stateless execution.

10. TREEMAP USAGE & THEORY
==================================================

Actual Code Usage:

FILE: src/main/java/com/releasepilot/feature/EvaluationService.java
CLASS: EvaluationService
METHOD: buildCacheKey(UUID environmentId, String flagKey, Map<String, Object> context)
LINE: 230
CODE: `String payload = environmentId + ":" + flagKey + ":" + objectMapper.writeValueAsString(new TreeMap<>(context));`

What is Stored:
- KEY: String (context attribute names, e.g. "country", "email", "userId").
- VALUE: Object (attribute values).

Why TreeMap is Used Here:
To achieve **Map Key Normalization (Canonicalization)** before generating the Redis cache key hash.
Standard HashMap iteration order is non-deterministic. If two requests pass identical context keys in different insertion orders:
Request A: `{"userId":"1", "country":"US"}`
Request B: `{"country":"US", "userId":"1"}`
A standard HashMap serialized to JSON might produce different strings, generating different SHA-256 hashes (Cache Miss).
Wrapping the context in `new TreeMap<>(context)` sorts the keys lexicographically ("country" before "userId"). Serialization yields identical JSON string payloads, guaranteeing cache key identity!

TreeMap Computer Science Fundamentals:
- Map: Key-value pair associative container.
- TreeMap Implementation: Red-Black Tree (self-balancing binary search tree).
- Time Complexity: O(log N) for insertion, lookup, and deletion (where N is number of keys in map).
- Ordering: Sorted according to natural key ordering (Comparable) or explicit Comparator.
- Comparison (TreeMap vs HashMap):
  - HashMap: O(1) average lookup/insert, backed by hash table array + linked lists/Red-Black trees (for bucket collisions), UNORDERED.
  - TreeMap: O(log N) lookup/insert, backed strictly by Red-Black Tree, ALWAYS SORTED by key.

Does TreeMap Have Anything To Do With Handling Millions of Users?
NO. In ReleasePilot, TreeMap is used locally per request on small context maps (typically 1 to 5 elements) purely to sort JSON keys for cache key hashing. It is NOT used as an in-memory database or user storage.

12. TRANSACTIONS & CONCURRENCY
==================================================

What Current Code Does:
1. @Transactional Annotation: Applied on Service methods (e.g. AuthService.register, FeatureFlagService.createFlag, EvaluationService.evaluateFlag).
2. Database Constraints: Relies on PostgreSQL unique indexes (`UNIQUE(organization_id, key)`, `UNIQUE(api_key)`, `UNIQUE(flag_id, environment_id)`) to reject duplicate entries under concurrent requests.
3. Exception Conversion: Unique constraint violations throw DataIntegrityViolationException at DB level.

What Could Be Improved (Gaps / Weaknesses):
1. Optimistic Locking: Entities lack `@Version` fields. Concurrent updates to flag rules will execute last-write-wins (lost update anomaly).
2. Pessimistic Locking: No `SELECT FOR UPDATE` queries used during rule updates.
3. Race Conditions on Auto-Provisioning: If two requests register with same organization name simultaneously, duplicate org check in AuthService might suffer read-then-write race condition if DB constraints fail.

--- 10 VERY DEEP QUESTIONS ---

Q1: Why bitwise shifting `((digest[0] & 0xFF) << 24) | ...` in HashUtils instead of String hashCode()?
DETAILED ANSWER: Java's `String.hashCode()` uses a simple polynomial hash ($s[0]*31^{n-1} + ...$) which suffers from high collision rates and non-uniform distribution across small ranges. Bitwise shifting the first 4 bytes of a SHA-256 cryptographic digest guarantees uniform mathematical entropy across [0, 99].
FILE: src/main/java/com/releasepilot/common/HashUtils.java
LIMITATION: SHA-256 calculation overhead is higher than hashCode().
IMPROVEMENT: MurmurHash3 could be used for faster non-cryptographic hashing.

Q2: Is the Redis cache invalidation currently consistent when flag rules are updated?
DETAILED ANSWER: NO. When an admin updates a targeting rule or flag state in FeatureFlagService, `@CacheEvict` is NOT called. Cache entries persist in Redis until their 30-second TTL expires.
FILE: src/main/java/com/releasepilot/feature/FeatureFlagService.java
LIMITATION: Stale flag evaluation results can be served up to 30s after rule changes.
POSSIBLE IMPROVEMENT: Add `@CacheEvict(value = "evaluations", allEntries = true)` or Redis Pub/Sub invalidation upon flag update.

Q3: What database concurrency issues exist in AuthService.register()?
DETAILED ANSWER: `register()` performs a non-atomic read-then-write check (`userRepository.existsByEmail`). Under heavy concurrent registration requests with the same email, two threads could pass `existsByEmail` simultaneously.
FILE: src/main/java/com/releasepilot/auth/AuthService.java
WHY: Relies on PostgreSQL unique constraint on `users(email)` to abort the second transaction with `DataIntegrityViolationException`.
IMPROVEMENT: Catch DataIntegrityViolationException in GlobalExceptionHandler and rethrow DuplicateResourceException.

Q4: Explain how Spring's @Transactional behaves during evaluationLogRepository.save() in EvaluationService.
DETAILED ANSWER: Because `evaluateFlag` is annotated with `@Transactional`, if `evaluationLogRepository.save(log)` fails due to a DB exception, the entire transaction (including any pending entity state changes) will roll back despite the try-catch block!
FILE: src/main/java/com/releasepilot/feature/EvaluationService.java
LIMITATION: Log insertion failure can break flag evaluation API response.
POSSIBLE IMPROVEMENT: Move evaluation logging to an asynchronous event listener (`@Async` or `@Transactional(propagation = Propagation.REQUIRES_NEW)`).

Q5: How does Jackson deserialize complex JSON flag types in parseTypedValue()?
DETAILED ANSWER: When `flagType == FlagType.JSON`, `objectMapper.readValue(rawValue, Object.class)` parses raw JSON string into a Java Map or List, which is returned inside `EvaluationResultDto.value`.
FILE: src/main/java/com/releasepilot/feature/EvaluationService.java -> parseTypedValue()

Q6: Why is `CustomUserDetailsService.loadUserById()` implemented in addition to `loadUserByUsername()`?
DETAILED ANSWER: JWT tokens store the user's UUID as the subject claim (not email). Storing immutable UUIDs in JWT claims prevents authentication breakdown if a user changes their email address.
FILE: src/main/java/com/releasepilot/security/CustomUserDetailsService.java

Q7: What happens if Redis goes down while `releasepilot.cache.enabled=true`?
DETAILED ANSWER: `getCachedResult()` and `putCachedResult()` check `if (cacheManager == null)`. However, if Redis connection drops, Spring Cache throws a `QueryTimeoutException` or `RedisConnectionFailureException`.
FILE: src/main/java/com/releasepilot/feature/EvaluationService.java
LIMITATION: Backend requests fail if Redis crashes.
POSSIBLE IMPROVEMENT: Implement a custom CacheErrorHandler bean returning null on Redis exceptions to fall back smoothly to PostgreSQL.

Q8: How does Flyway ensure migration scripts are not tampered with after execution?
DETAILED ANSWER: Flyway calculates a SHA-256 checksum for every `.sql` file and records it in `flyway_schema_history` table. If a previously applied migration file is edited, Flyway halts application startup with a ChecksumMismatchException.

Q9: What security vulnerability exists in `SecurityConfig` CORS configuration?
DETAILED ANSWER: `configuration.setAllowedOriginPatterns(List.of("*"))` combined with `setAllowCredentials(true)` reflects any Origin header, exposing JWT APIs to Cross-Origin Request Forgery / credential leaks if hosted publicly.
FILE: src/main/java/com/releasepilot/security/SecurityConfig.java

Q10: Why does `InsightService.assessRisk()` flag traffic as `HIGH` risk when maxShare > 0.95?
DETAILED ANSWER: If 95%+ of traffic evaluates to a single variant during a configured 50/50 rollout, it indicates potential rule misconfiguration, sticky hashing anomalies, or zero traffic reaching new feature code.
FILE: src/main/java/com/releasepilot/audit/InsightService.java -> assessRisk()
